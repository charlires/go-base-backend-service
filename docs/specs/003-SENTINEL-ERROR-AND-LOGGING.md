# Sentinel Error and Logging Strategy

## Sentinel Error Strategy

1. **Define Sentinel Errors**: Sentinel errors are predefined, exported error variables that represent specific error conditions, including domain errors, repository errors, and **input validation errors** (e.g., `ErrInvalidInput`). They must all be defined in a single central file `internal/core/errors.go`, regardless of domain, and follow a consistent naming convention (e.g., `ErrUserNotFound`, `ErrInvalidInput`).
2. **Use Sentinel Errors in Services**: When a service encounters an error condition that matches a sentinel error, it should return the corresponding sentinel error instead of creating a new error instance. This allows for consistent error handling and easier error comparison in tests and higher layers.
3. **Wrapping Errors with Context**: Always use `fmt.Errorf` with the `%w` verb to wrap a sentinel error whenever there is either (a) an underlying dependency error to preserve (e.g., a repository error), or (b) additional context required to fully understand the error condition (e.g., input validation failures, business rule violations). The sentinel error must always be included in the wrap so that `errors.Is` comparisons work correctly at higher layers.
4. **Always Return Service-Level Sentinel Errors**: Services must never propagate raw errors from dependencies (e.g., repository errors) directly to the caller. Every error returned from a service must be a sentinel error (or wrapped with one using `fmt.Errorf`), ensuring that higher layers only deal with service-level error semantics.
4. **Error Comparison**: When handling errors in higher layers (e.g., HTTP adapters), use `errors.Is` to check if the error matches a specific sentinel error. This allows for consistent error handling and response generation based on the type of error.

## Logging Strategy

1. **Use a Logging Library**: Use a structured logging library `slog` from the Go standard library for logging throughout the application. This allows for consistent log formatting and easy integration with log management systems.
2. **Log at Appropriate Levels**: Use different log levels (e.g., `Error`, `Debug`) to indicate the severity of log messages. Use `Error` level for logging errors and `Debug` level for tracing execution flow throughout the application.
3. **Ensure Domain Structs Define LogValue() Method**: To enable structured logging of domain entities, ensure that all domain structs implement the `LogValue() slog.Value` method. This method must **omit sensitive fields** (e.g., passwords, tokens, personal data) to prevent accidental exposure in logs, aligning with rule #5 below.
4. **Include Context in Logs**: When logging errors or important events, include relevant context (e.g., user ID, playlist ID) in the log messages to facilitate debugging and monitoring.
5. **Avoid Logging Sensitive Information**: Ensure that sensitive information (e.g., passwords, personal data) is not logged to prevent security risks and comply with privacy regulations. Sensitive fields must be excluded directly in the `LogValue()` method of the relevant domain struct.
6. **Centralize Log Configuration**: Configure the logging output, format, and level in a central location (e.g., `main.go`) to ensure consistency across the application and allow for easy adjustments as needed. *(Logger injection strategy to be defined.)*
7. **Log Levels by Layer**: `Error` level logs must only be emitted from the HTTP adapter layer, as it is the final layer responsible for handling and responding to errors. All layers (services, repositories, adapters) must emit `Debug` level logs on **every function entry**, capturing relevant input parameters to facilitate tracing and troubleshooting.
